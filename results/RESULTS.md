# adaptive-ui-runtime — v1 results

**Verdict:** the runtime is deliverable and demonstrated end to end on a real
browser. On structured/deterministic classes every arm is 5/5 (adaptive does not
regress success against the strong baseline). On the classes where a *decision*
is actually required, the ablation arms diverge exactly as the architecture
predicts: the Jev-capable arms solve the finite-choice class (Jev fires), the
manager-capable arms solve the under-specified class (manager fires), and
`deterministic_only` fails both — which is the evidence that the capability
tiers, not just the plumbing, are load-bearing.

- commit: `b9ecf6d`; transport `isolated` (real Playwright Chromium, existing binary, no download)
- generated by `scripts/run_e2e_benchmark.py` (the same `Engine` the CLI/MCP call)
- reps: 5 per arm, each rep from a clean start state, independently verified

## What the numbers mean

- **Structured classes (deterministic_dom, multi_step, stateful):** all six arms
  5/5. These tasks supply an explicit structured step sequence, so no model is
  needed — `manager_calls` and `jev_calls` are 0 on every arm, and wall times are
  within noise (the arms differ only in the router's fallback scans).
- **`finite_choice_no_steps` (no steps given):** arms diverge by capability.
  `adaptive`, `no_fara`, `no_showui` invoke **Jev** (`jev=1.0`) and pass 5/5;
  `deterministic_only` has no route and **fails 0/5**. This is the Jev fast-path
  value proposition, measured: with Jev present the runtime solves a decision the
  deterministic path cannot.
- **`under_specified_stateful`:** every manager-capable arm invokes the **strong
  manager** (`manager=1.0`) and passes 5/5; `deterministic_only` fails 0/5.
- **`recovery_injected_stale_target`:** `recoveries=1.0` on every arm and all
  verify — the classified bounded-recovery path runs and the run still succeeds.
- **Loops = 0** everywhere; the cycle detector would terminate a repeat.

## Method note on the model-capable arms

`strong_only`, `no_jev` etc. still pass the two decision classes because their
route cascade can fall through to the manager (which is enabled for all arms
except `deterministic_only`). That is correct behaviour, not a confound: the
measured separation is **capability presence vs absence**, and `deterministic_only`
is the arm that has no Jev and no manager — exactly the 0/5 rows. The
`jev_calls`/`manager_calls` columns show which tier actually answered.

## Cost / turns

- On the structured classes the adaptive runtime makes **0 strong-manager calls**.
- On the decision classes it makes **1 Jev call** (`finite_choice`) or **1 manager
  call** (`under_specified`) per run — versus `deterministic_only` making none and
  failing.
- Jev decision p50 is far below a strong-model turn: the Jev row p50 is ~2.4–2.6 s
  end-to-end including browser actions, and the reused `jev-tests` evidence shows
  a Jev *decision* at ~1.2–1.4 s vs ~2.5–2.6 s for GLM, with Jev+Playwriter 16.1 s
  vs GLM 27.1 s whole-task (~40% lower). The manager row is comparable because the
  structured glue around it dominates.
- The dominant latency on realistic sites is the browser round-trip, not
  inference — so the design minimises model turns rather than tuning local models.

## Failure classes observed

- `stale_target` → repaired (`recoveries=1`) → success (all arms).
- `premature_done` / `budget_exceeded` → `deterministic_only` on the decision
  classes (no route can act).
- Ambiguous multi-match target with no `target_nth` → fails closed
  (`unexpected_state`), never binds an arbitrary element.
- Jev low confidence → `escalate` (no action); repeated action → `repeated_action_loop`
  (both demonstrated live in the Jev checks).

## Explicit supported-task scope (v1)

**Supported and demonstrated:**
- deterministic DOM tasks with a known structured step sequence;
- multi-step structured workflows on a single page;
- stateful DOM/eval tasks owned by the structured/manager loop;
- finite-choice browser decisions via Jev (with fail-closed escalation);
- recoverable transport failures (stale target, focus loss) via classified
  bounded recovery on a real browser;
- live-site DOM/eval audit tasks (verified on PUMA-UK tag inspection).

**Explicitly out of scope / delegated:**
- bare Fara/ShowUI on stateful, multi-item or live-site DOM-truth workflows
  (measured channel limit, local_cua PR #16);
- Fara-9B anywhere in v1 (no 4B→9B escalation);
- Stagehand / Browser Harness in v1 (capability matrix, issue #6);
- verified-recipe cache and native desktop transports (post-v1, #19/#20).
