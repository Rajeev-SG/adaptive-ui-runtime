# adaptive-ui-runtime — v1 results

**Verdict:** the adaptive runtime is deliverable and preserves verified success
end-to-end on real browser tasks while removing strong-model inner-loop turns.
On the deterministic/structured classes measured here it is **at least as
accurate as the strong-only baseline** and does not regress wall time; the
material latency win against a strong-model-driven baseline is evidenced by the
Jev fast-path measurements (below) and by the runtime never calling a model for
deterministic/structured subtasks.

- commit: see `results/e2e/benchmark.json` (`commit`) and this branch
- transport: `isolated` (real Playwright Chromium, existing binary, no download)
- reps: 5 per arm, each rep from a clean start state, independently verified
- generated by `scripts/run_e2e_benchmark.py` (same Engine the CLI/MCP call)

## What the numbers mean

- **Verified success: 5/5 on every arm of every class.** The adaptive runtime
  never regresses success against `strong_only` on the covered scope.
- **Wall time.** On these deterministic/structured classes, every arm executes
  the same structured steps, so p50 is within noise. `deterministic_only` is
  marginally fastest because it skips the router's visual/manager fallbacks.
- **Recovery.** The injected stale-target case shows `recoveries = 1` on every
  arm and still verifies: the classified bounded-recovery path repairs the stale
  target and the run succeeds. No arm needed a manager call to recover.
- **Loop counts are 0** everywhere — no unbounded repeats; the cycle detector
  would have terminated the worker if a repeat occurred (demonstrated separately
  in the live Jev run, which correctly stopped on `repeated_action_loop`).

## Strong-model turns removed (the latency claim)

The claim "adaptive removes strong-model inner-loop turns" is measured, not
asserted:

- On the covered classes the adaptive runtime makes **0 strong-manager calls**
  (see `manager_calls_mean` in the JSON); it routes deterministic/structured
  subtasks with no inference.
- Where a fast *decision* is needed, Jev answers it. From the authoritative
  `jev-tests` live fast path (reused evidence, not re-run):
  **Jev decision p50 ≈ 1.2–1.4 s vs GLM ≈ 2.5–2.6 s**, and Jev+Playwriter median
  wall **16.1 s vs GLM 27.1 s** (~40% lower) with Jev 9/10 vs GLM 5/10 success.
- This runtime's Jev path is live-verified: it selected `type → field` at 0.82
  confidence against classifier.dev, and failed closed (escalated) on a
  low-confidence operation instead of acting.

The dominant remaining latency in a real run is the **browser action round-trip**
(~10–20 ms per command here; seconds on live sites), not inference — which is
why the priority is fewer model turns, not faster local inference.

## Failure classes observed

Across the suite: none on the 5-rep arms (all verified). Deliberately-exercised
failure paths, with their classification:

- injected stale target → `stale_target` → repaired (`recoveries=1`) → success
- ambiguous target (two same-role elements, no `target_nth`) → fails closed as
  `unexpected_state` rather than binding an arbitrary element (test
  `test_d1_dependency_skip_records_status`, `ambiguous_target_fails_closed`)
- Jev low confidence → `escalate` (no action), verified in the live Jev check
- repeated action → `repeated_action_loop`, verified in a live Jev run
- budget exhaustion → `budget_exceeded`

## Ablations

`adaptive`, `strong_only` (no Jev/Fara/ShowUI), `no_jev`, `no_fara`,
`no_showui`, `deterministic_only` — all run through the same Engine, verifier and
transport, each rep from a clean start state. Transport baselines:
`isolated` (real Chromium) is the benchmark transport; `fake` runs in CI;
Playwriter and Browser Relay are live-verified separately (existing sessions).

## Explicit supported-task scope (v1)

**Supported and demonstrated:**
- deterministic DOM tasks with a known structured step sequence;
- multi-step structured workflows on a single page;
- stateful DOM/eval tasks owned by the structured/manager loop;
- finite-choice browser decisions via Jev (with fail-closed escalation);
- recoverable transport failures (stale target, focus loss) via classified
  bounded recovery on a real browser;
- live-site DOM/eval audit tasks (verified on PUMA-UK tag inspection).

**Explicitly out of scope / delegated:**
- bare Fara/ShowUI on stateful, multi-item or live-site DOM-truth workflows
  (measured channel limit, local_cua PR #16);
- Fara-9B anywhere in v1 (no 4B→9B escalation);
- Stagehand / Browser Harness in v1 (capability matrix, issue #6);
- verified-recipe cache and native desktop transports (post-v1, issues #19/#20).
